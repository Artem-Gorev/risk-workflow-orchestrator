# Требования к MVP оркестратора оценки рисков

Оркестратор управляет ручными и регламентными расчётами рисков. Он ставит заявки в общую очередь, запускает совместимые расчёты параллельно и откладывает задачи при конфликте доступа к данным. История запусков показывает, какие задачи ожидали, когда они выполнялись и чем завершились. [Примеры пересечений](business-analysis.md), [критерии приёмки](#критерии-приёмки).

## Границы MVP

Прототип включает диспетчер, менеджер ресурсов, исполнителей для синтетических данных, REST API и веб-интерфейс запуска и мониторинга. Демонстрационный стенд показывает, как ограничения доступа влияют на порядок выполнения и целостность результатов.

Единица запуска — отдельная заявка на расчёт с набором входных и выходных ресурсов. [Анализ конфликтов](business-analysis.md), [компоненты системы](architecture.md).

## Функциональные требования

### FR-01

**Единая очередь.** Ручной запуск из интерфейса и заявка от планировщика передают код процесса, расчётную дату и источник запуска одному сервису постановки. Сервис назначает новым задачам место в общей очереди и записывает событие постановки. При включённом `joinActive` допустимо присоединение к существующей задаче по правилам FR-10. Ограничения ресурсов одинаковы для обоих источников. Запрос с неизвестным процессом или недопустимой датой отклоняется до создания задачи.

### FR-02

**Определение области доступа.** Сервис постановки вычисляет полный набор доступов из серверного реестра процессов и параметров запуска. Два доступа пересекаются, если у них одинаковый ключ ресурса и есть общая область данных. Дату и режим доступа к входам и выходам определяет контракт процесса. [Проект модели Job и Resource](architecture.md).

### FR-03

**Совместимость и атомарное резервирование.** Для каждого запрошенного доступа диспетчер сравнивает его с активными резервированиями. Пары для разных ключей или непересекающихся областей совместимы. Для совпавших ключей и пересекающихся областей действует матрица.

| Запрошенный доступ / активный доступ | `READ` | `WRITE` |
| --- | --- | --- |
| `READ` | Совместимы | Конфликт |
| `WRITE` | Конфликт | Конфликт |

При конфликте хотя бы одной пары задача ждёт без резервирования ресурсов. Если все пары совместимы и у исполнителя есть место, диспетчер резервирует весь набор одной атомарной операцией до передачи задачи исполнителю.

### FR-04

**Ожидание и параллельный запуск.** Диспетчер повторно проверяет ожидающие задачи при освобождении ресурсов или места. При свободном месте совместимая задача может стартовать, пока другая ждёт ресурс. Порядок задаётся эффективным приоритетом с учётом времени ожидания, затем номером постановки. Защита долго ожидающего кандидата может задержать более позднюю несовместимую с ним задачу с причиной `QUEUE_FAIRNESS`. [Порядок выбора задач](architecture.md).

### FR-05

**Завершение, результат и освобождение ресурсов.** При успешном обычном расчёте система публикует целостный результат, сохраняет его по задаче и освобождает все её резервирования. При ошибке попытки система фиксирует код и описание, освобождает ресурсы и сохраняет последнее успешно опубликованное значение, если оно было. Восстанавливаемый сбой допускает до трёх попыток всего, остальные ошибки дают `FAILED` сразу. Исход каждой попытки отражается в истории. [Контракт Worker](architecture.md).

### FR-06

**Статусы и причины ожидания в интерфейсе.** Через интерфейс пользователь подаёт ручные заявки и просматривает очередь, активные и завершённые задачи. Для каждой задачи видны процесс, расчётная дата, источник запуска, статус и история переходов. В деталях доступны результат или ошибка. При конфликте интерфейс показывает ресурс, область, режимы доступа и блокирующие задачи по данным API. Интерфейс также показывает `NO_WORKER_SLOT`, `QUEUE_FAIRNESS` и сообщение при недоступности API. [Контракт API](architecture.md#rest-api).

### FR-07

**Журнал событий и наблюдаемый порядок.** Система записывает постановку и присоединение заявки, ожидание и смену его причины, резервирование, фактический старт и исход каждой попытки. Завершение, повторная постановка и остановка фиксируют освобождение удерживаемых ресурсов. События содержат идентификатор задачи и время, а общий порядок в одной очереди позволяет восстановить последовательность выполнения. API отдаёт историю для таймлайна и сквозных проверок. [Журнал событий](architecture.md).

### FR-08

**Проверяемые синтетические расчёты.** Исполнитель читает объявленные ресурсы, пишет результат в объявленную область и поддерживает управляемую длительность и воспроизводимую ошибку в тестовых сценариях. Результаты сверяются с контрольными значениями для `2026-11-26` и `2026-11-27`. Сводка проверяет наличие исходных оценок и совпадение ревизий коэффициентов для кредитного и рыночного расчётов. [Синтетическая модель](business-analysis.md).

### FR-09

**Отмена и остановка.** `/cancel` доступен в `QUEUED` и `WAITING`. Если резервирование зафиксировано раньше отмены, API возвращает конфликт состояния. `/stop` также доступен в `STARTING` и `RUNNING`. При остановке система освобождает ресурсы и отклоняет дальнейшую публикацию остановленной попыткой. Обе операции фиксируют `CANCELLED` и событие, снимающее задачу с диспетчеризации. [Жизненный цикл](architecture.md), [ответ API](architecture.md#rest-api).

### FR-10

**Повторные запуски и повторы доставки.** При обычной постановке повтор доставки с тем же ключом и параметрами возвращает исходный `jobId`. Повтор ключа с другими параметрами отклоняется. Ручные и регламентные ключи раздельны. По умолчанию новая заявка создаёт отдельную задачу. При включённом `joinActive` заявка может присоединиться к незавершённой задаче с совпадающими процессом, датой, версией и приоритетом. Явный перезапуск создаёт новый расчёт с актуальными входами, а `/replay` создаёт задачу по сохранённому снимку. История хранит результаты каждой задачи, а воспроизведение сохраняет текущие значения ресурсов. [Правила повторов](architecture.md).

## Нефункциональные требования

### NFR-01

**Безопасность конкурентного доступа.** Согласованность сохраняется при одновременной постановке, диспетчеризации, завершении и отмене. Конфликтующие резервирования активируются последовательно. Атомарный захват исключает циклы ожидания из частично удерживаемых наборов. При сбое расчёта или публикации результата система фиксирует ошибку и освобождает ресурсы.

### NFR-02

**Воспроизводимость проверки.** Одинаковые входы и коэффициенты дают одинаковые контрольные значения. Для проверки порядка интеграционные тесты управляют длительностью синтетических задач и сопоставляют события, включая старт исполнителя. Сценарий параллельного запуска проверяется как минимум с двумя местами у исполнителя.

### NFR-03

**Запускаемость демонстрационного стенда.** Собранный MVP запускается через Docker Compose и доступен по ссылке на сервере. Через интерфейс стенда можно запустить расчёты на синтетических данных и проверить результат по истории.

## Критерии приёмки

Критерии описывают ожидаемые наблюдения при проверке прототипа. Каждый сценарий использует отдельный набор синтетических данных со значениями для `D1` и `D2` из [модели](business-analysis.md).

В проверках порядка запуска тест удерживает первую задачу после старта, пока вторая не достигнет ожидаемого состояния. Порядок событий определяется по `eventId`. Два интервала выполнения пересекаются, если оба события `JOB_STARTED` предшествуют событиям освобождения соответствующих попыток. Для конфликтующей пары освобождение первой попытки предшествует `JOB_RESERVED` второй. [Журнал событий](architecture.md).

| Критерий | Условия | Наблюдаемый результат | Требования |
| --- | --- | --- | --- |
| AC-01 | Два места у исполнителя, `joinActive=false`. Ручной `credit-risk` за `D1` работает. Планировщик подаёт `credit-risk` за `D1`. | API показывает две разные задачи с источниками `MANUAL` и `SCHEDULED`. Вторая переходит в `WAITING` с `WRITE/WRITE` на `credit_risk[D1]` и ID первой задачи. Резервирование второй следует за завершением первой. Обе успешно вычисляют `10`. | [FR-01](#fr-01), [FR-03](#fr-03), [FR-07](#fr-07) |
| AC-02 | Два пользователя подают `credit-risk` за `D1` и `D2`, есть два места. | Оба старта наблюдаются до любого завершения. Сохранены разные дневные значения `10` и `15`, чтение общего справочника совместимо. | [FR-02](#fr-02), [FR-03](#fr-03), [FR-08](#fr-08), [NFR-02](#nfr-02) |
| AC-03 | В одном прогоне работают `credit-risk` и `market-risk` за `D1`. В другом `credit-risk` за `D1` уже работает, `market_risk[D1] = 10` и `liquidity_risk[D1] = 30` подготовлены, затем подаётся `risk-summary` за `D1`. | В первой паре оба запускаются до любого завершения. | AC-04 | `credit-risk` за `D1` поступает, пока `refresh-parameters` за `D2` держит `WRITE` на общем справочнике. Отдельная проверка менеджера ресурсов охватывает общую и дневную области одного ключа, дневные области разных дат и разные ключи. | Читатель ждёт на `risk_parameters[*]`, после успешного обновления читает новые коэффициенты и выдаёт `15`. Общая область пересекается с дневной того же ключа. Два разных дневных раздела и разные ключи дают пустое пересечение. | [FR-02](#fr-02), [FR-03](#fr-03), [FR-08](#fr-08) |

Следом поступает C (`liquidity-risk` за `D1`). | В журнале `JOB_WAITING(B)` раньше `JOB_STARTED(C)`, `JOB_STARTED(C)` раньше `JOB_SUCCEEDED(A)`, а `JOB_RESERVED(B)` позже `JOB_SUCCEEDED(A)`. | [FR-04](#fr-04), [FR-07](#fr-07), [NFR-02](#nfr-02) |

После завершения первой её терминальная запись предшествует резервированию полного набора второй. | [FR-03](#fr-03), [NFR-01](#nfr-01) |
| AC-07 | Исходное значение `credit_risk[D1]` равно `10`, после обновления коэффициентов новый расчёт даёт `15`. Проверяются ошибка расчёта и откат публикации, пока другая задача ждёт тот же ресурс. Для отказа передачи до старта проверяются однократный отказ и отказ на каждой попытке. | При ошибке расчёта или публикации задача переходит в `FAILED`, ресурсы освобождаются, прежнее значение `10` доступно до публикации следующей задачи. При отказе передачи у отклонённой попытки есть освобождение ресурсов и отсутствует `JOB_STARTED`. Однократный отказ даёт `JOB_RETRY_SCHEDULED` и успешную следующую попытку. Отдельные варианты включают ошибку расчёта и временную недоступность API. | Статусы и причины соответствуют API. При недоступности API видно сообщение о недоступности. | [FR-01](#fr-01), [FR-06](#fr-06), [FR-07](#fr-07) |
| AC-09 | В отдельных прогонах `/cancel` вызывается для ожидающей B и для B после `JOB_RESERVED`. В третьем прогоне `/stop` вызывается для `RUNNING`. | Для ожидающей задачи виден `JOB_CANCELLED`, её старт отсутствует. Для уже зарезервированной `/cancel` возвращает `409`. После `/stop` задача переходит в `CANCELLED`, освобождает ресурсы и прежняя попытка не публикует результат. | [FR-07](#fr-07), [FR-09](#fr-09), [NFR-01](#nfr-01) |
| AC-10 | При `joinActive=false` проверяются ручные запросы с тем же ключом и параметрами, с тем же ключом и другой датой, с новым ключом, а также повтор доставки одного срабатывания регламента. Отдельный прогон с `joinActive=true` подаёт две заявки с разными ключами, пока первая задача активна, с одинаковыми процессом, датой, версией и приоритетом. | Без объединения повтор доставки возвращает прежний `jobId` и единственное `JOB_QUEUED`. Изменение даты с тем же ключом даёт `409`, а новый ручной запуск и регламент получают отдельные задачи. При включённом объединении вторая заявка возвращает `jobId` первой, в истории появляется `JOB_TRIGGER_JOINED`. | [FR-01](#fr-01), [FR-10](#fr-10) |
| AC-11 | Сначала за `D1` выполняются кредитный, рыночный расчёты и расчёт ликвидности. После обновления коэффициентов за `D2` повторяется только кредитный расчёт. Далее проверяются сводка из разных ревизий и отдельный прогон с отсутствующим входом. | В истории два кредитных результата `10` и `15`, текущее значение равно `15`. Сводка из разных ревизий завершается с `MIXED_REVISIONS`, а при отсутствующей оценке — с `INPUT_NOT_FOUND`. Оба ошибочных запуска завершаются без публикации сводки. | [FR-05](#fr-05), [FR-08](#fr-08), [FR-10](#fr-10), [NFR-02](#nfr-02) |
| AC-12 | API получает три отдельные заявки — с неизвестным процессом, несуществующей датой `2026-02-30` и без даты. | API сообщает об ошибке валидации. После трёх запросов число задач и событий `JOB_QUEUED` прежнее. | [FR-01](#fr-01), [FR-06](#fr-06) |
| AC-13 | Одновременно поступают 12 заявок `credit-risk`, по шесть на `D1` и `D2`, с уникальными ключами и минимум двумя местами у исполнителя. | Все 12 имеют отдельные ID и завершаются успешно. Сопоставление резервирований и освобождений по `eventId` даёт максимум одного писателя для каждого дневного выхода и ноль активных резервирований в конце. Значения выходов `10` и `15`. | [FR-02](#fr-02), [FR-03](#fr-03), [FR-07](#fr-07), [NFR-01](#nfr-01) |
| AC-14 | MVP работает на демонстрационном стенде, сценарий AC-05 выполняется через интерфейс по опубликованному адресу. | Сервисы стартуют через Docker Compose, интерфейс доступен по ссылке. Результаты и последовательность AC-05 видны в истории API и UI. | [FR-06](#fr-06), [NFR-03](#nfr-03) |
| AC-15 | Единственное место занимает A (`credit-risk` за `D1`). Затем с одинаковым приоритетом поступают B (`liquidity-risk` за `D1`) и C (`credit-risk` за `D1`). Обе переходят в ожидание. A завершается до того, как любая из них ждёт 30 секунд. | B с меньшим `queueSequence` резервируется первой из двух совместимых с освободившимися ресурсами задач. Причина ожидания C меняется с `RESOURCE_CONFLICT` на `NO_WORKER_SLOT`. API и `JOB_WAIT_REASON_CHANGED` показывают новую причину, а C резервируется после завершения B. | [FR-04](#fr-04), [FR-06](#fr-06), [FR-07](#fr-07) |
