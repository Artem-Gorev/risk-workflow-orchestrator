# Бизнес-анализ MVP оркестратора оценки рисков

Аналитики по рискам запускают расчёты вручную, а часть расчётов выполняется по расписанию. Одновременные запуски могут обращаться к одним и тем же данным. Например, если ручной и регламентный расчёты записывают результат за одну дату, один из них может затереть результат другого.

Оркестратор ставит заявки в общую очередь и определяет, какие из них могут выполняться одновременно. Задача ждёт, если её чтение или запись конфликтует с другим расчётом. В панели RiskFlow видны статус, причины ожидания и результат. [Требования к системе](requirements.md), [архитектура](architecture.md).

[Модель процессов](#синтетическая-модель-процессов) · [Сценарии запуска](#сценарии-одновременного-запуска) · [Анализ с помощью ИИ](#анализ-с-помощью-ии)

## Как запускается расчёт

- **Ручной запуск.** Аналитик выбирает процесс и расчётную дату в панели RiskFlow. Панель отправляет заявку в `POST /api/v1/jobs` и показывает статус задачи.
- **Регламентный запуск.** Планировщик создаёт заявку на заданный процесс по расписанию. Расчётную дату определяет регламент. Заявка поступает в ту же очередь, что и ручные запуски. [Правило выбора расчётной даты](architecture.md).
- **Расчётная дата** определяет, за какой день процесс читает и записывает данные в ресурсах с дневной разбивкой. У общего ресурса область доступа охватывает весь набор данных при любой расчётной дате. Система определяет пересечения по ресурсу и области доступа. Время запуска и идентификатор инициатора служат для истории. [FR-01](requirements.md#fr-01), [FR-02](requirements.md#fr-02).

## Синтетическая модель процессов

Модель включает четыре вида оценки риска, сводный расчёт и обновление общих коэффициентов. Каждый процесс можно запустить вручную или по расписанию. В демонстрации регламент запускает `credit-risk`. Денежные суммы даны в условных единицах.

В контрольных сценариях используются `D1` (`2026-11-26`) и `D2` (`2026-11-27`). По умолчанию доступны даты с `2026-11-23` по `2026-11-30` включительно. Границы задаются параметрами `SYNTHETIC_START_DATE` и `SYNTHETIC_END_DATE`. Обозначение `[D]` указывает на независимый раздел за расчётную дату заявки, `[*]` — на весь ресурс. `READ` означает чтение, `WRITE` — запись.

### Данные и доступы процессов

| Процесс | Ресурс | Область доступа | Режим |
| --- | --- | --- | --- |
| `credit-risk` — расчёт кредитного риска | `credit_exposures` — просроченные суммы | `[D]` | `READ` |
| `credit-risk` | `risk_parameters` — коэффициенты расчёта | `[*]` | `READ` |
| `credit-risk` | `credit_risk` — оценка кредитного риска | `[D]` | `WRITE` |
| `market-risk` — расчёт рыночного риска | `market_positions` — суммы по позициям | `[D]` | `READ` |
| `market-risk` | `risk_parameters` — коэффициенты расчёта | `[*]` | `READ` |
| `market-risk` | `market_risk` — оценка рыночного риска | `[D]` | `WRITE` |
| `liquidity-risk` — расчёт риска ликвидности | `cash_flows` — поступления и выплаты | `[D]` | `READ` |
| `liquidity-risk` | `liquidity_risk` — дефицит ликвидности | `[D]` | `WRITE` |
| `operational-risk` — расчёт операционного риска | `incident_losses` — потери по инцидентам | `[D]` | `READ` |
| `operational-risk` | `operational_risk` — оценка операционного риска | `[D]` | `WRITE` |
| `risk-summary` — расчёт сводного показателя | `credit_risk` | `[D]` | `READ` |
| `risk-summary` | `market_risk` | `[D]` | `READ` |
| `risk-summary` | `liquidity_risk` | `[D]` | `READ` |
| `risk-summary` | `risk_summary` — сумма трёх оценок | `[D]` | `WRITE` |
| `refresh-parameters` — расчёт коэффициентов из дневного набора | `parameter_inputs` — исходные проценты | `[D]` | `READ` |
| `refresh-parameters` | `risk_parameters` — коэффициенты для всех дат | `[*]` | `WRITE` |

### Входы и контрольные результаты

| Ресурс или показатель | D1 | D2 | Правило расчёта |
| --- | --- | --- | --- |
| `credit_exposures` | `40, 60` | `50, 100` | Входные просроченные суммы |
| `market_positions` | `−30, 20` | `−40, 20` | Входные суммы со знаком |
| `cash_flows` | `70, 100` | `80, 110` | Поступления, выплаты |
| `incident_losses` | `4, 6` | `12, 18` | Потери по отдельным инцидентам |
| `parameter_inputs` | `10%, 20%` | `15%, 25%` | Кредитный и рыночный проценты |
| `credit_risk` | `10` | `15` | Сумма просроченных сумм × кредитный коэффициент |
| `market_risk` | `10` | `12` | Сумма абсолютных значений позиций × рыночный коэффициент |
| `liquidity_risk` | `30` | `30` | Максимум из нуля и разности выплат и поступлений |
| `operational_risk` | `10` | `30` | Сумма потерь по инцидентам |
| `risk_summary` | `50` | `57` | Сумма трёх сохранённых оценок за дату |

Контрольные значения рассчитаны с начальной ревизией коэффициентов `0,10` для кредитного риска и `0,20` для рыночного. `refresh-parameters` переводит проценты в доли и публикует новую ревизию обоих коэффициентов в `risk_parameters[*]`. После обновления за `D2` следующий обычный `credit-risk` за `D1` возвращает `15` при тех же входных суммах, поскольку текущая ревизия справочника общая для всех дат.

`risk-summary` суммирует кредитную, рыночную оценки и оценку риска ликвидности за выбранную дату. Операционный риск публикуется отдельно. Обычная сводка читает три опубликованные оценки. Если одной из них ещё нет, задача завершается с `INPUT_NOT_FOUND`. Кредитная и рыночная оценки должны ссылаться на одну ревизию одного справочника коэффициентов. При разных ревизиях сводка завершается с `MIXED_REVISIONS`, а при отсутствии данных о ревизии — с `REVISION_UNKNOWN`. При новых запусках текущее значение ресурса соответствует последней успешной публикации, а история хранит результат каждой задачи. [FR-05](requirements.md#fr-05), [FR-08](requirements.md#fr-08), [FR-10](requirements.md#fr-10).

## Сценарии одновременного запуска

Сценарии показывают поведение отдельных задач при выключенном объединении заявок (`joinActive=false`).

| Сценарий | Какие данные пересекаются и к чему это приводит | Условия параллельного выполнения |
| --- | --- | --- |
| Ручной запуск совпал с регламентным | Ручной и регламентный `credit-risk` за `D1` читают общие входы совместимо, но оба пишут в `credit_risk[D1]`. Одновременная запись делает итог зависимым от порядка записи и может затереть один из результатов. При работающем первом запуске второй ждёт освобождения области. | Совпадение времени или типа процесса само по себе не ограничивает запуск. Например, ручной `credit-risk` за `D2` совместим с регламентным за `D1`, пока общий справочник доступен для чтения и есть место у исполнителя. [FR-01](requirements.md#fr-01), [FR-03](requirements.md#fr-03), [FR-04](requirements.md#fr-04). |
| Несколько пользователей запускают один процесс за разные даты | `credit-risk` за `D1` и `D2` читает разные разделы `credit_exposures`, пишет в разные разделы `credit_risk` и совместимо читает `risk_parameters[*]`. Запись в общий ресурс увеличивает область конфликта. Например, `refresh-parameters` за `D2` заставит ждать читателя `credit-risk` за `D1`, если обновление уже зарезервировало справочник. | Разделы действительно изолированы, а все совпадающие области имеют совместимые режимы. Если один и тот же процесс пишет в общую область, его запуски за разные даты сериализуются. [FR-02](requirements.md#fr-02), [FR-03](requirements.md#fr-03). |
| Несколько пользователей запускают разные процессы за одну дату | Для `credit-risk` и `risk-summary` за `D1` есть `WRITE/READ` на `credit_risk[D1]`. При активной записи сводка ждёт, чтобы прочитать опубликованное значение. Если сводка первой зарезервировала чтение, расчёт ждёт её завершения. | `credit-risk` и `market-risk` за `D1` используют разные выходы и только читают общие `risk_parameters[*]`. `liquidity-risk` за `D1` вообще не пересекается с `credit-risk`. Обе пары совместимы при наличии двух мест у исполнителя. [FR-03](requirements.md#fr-03), [FR-04](requirements.md#fr-04). |

## Анализ с помощью ИИ

ИИ сформулировал гипотезы о причинах конфликтов и задержек. Проверка на синтетических данных включала сравнение областей и режимов доступа, построение графа ожидания при частичном захвате и сравнение двух политик очереди при двух местах у исполнителя. Для измерения частоты конфликтов и длительности ожидания в рабочей системе понадобятся эксплуатационные данные. Сквозная проверка прототипа описана в [критериях приёмки](requirements.md).

### Запросы к ИИ

**Запрос 1**

> Для ручного и регламентного запуска credit-risk за D1, для двух запусков credit-risk за D1 и D2 и для пары credit-risk D1 / refresh-parameters D2 перечисли совпадающие области и режимы доступа. В каком случае общая дата даёт конфликт, а в каком разные даты всё равно пересекаются?

**Запрос 2**

> Для запусков разных процессов за D1 сравни пары credit-risk / market-risk и credit-risk / risk-summary. Затем проверь на двух ресурсах X и Y, может ли поштучный захват с удержанием уже взятого ресурса образовать цикл, и что меняется при атомарном захвате.

**Запрос 3**

> Есть два места у исполнителя. Пока ручной credit-risk за D1 выполняется, регламентный credit-risk за D1 стоит первым в очереди, а следующий liquidity-risk за D1 независим. Сравни порядок событий при просмотре только головы очереди и при выборе самой ранней совместимой задачи.

### Гипотеза → проверка на модели → вывод → требование

| Запрос | Гипотеза | Проверка на синтетической модели | Вывод и требование |

[FR-04](requirements.md#fr-04), [FR-07](requirements.md#fr-07). |
